# Contributing

## Repo layout

- Go code: `scripts/syllable-cli/` — `go build` and `go test` run from here.
- `Casks/syllable.rb` — auto-generated by GoReleaser, do not hand-edit.
- `.goreleaser.yaml` and `.github/workflows/` — release pipeline config.
- `scripts/syllable-cli/internal/spec/openapi.json` — embedded OpenAPI spec; the CLI's source of truth for endpoints and schemas.

## Public repo hygiene

This repository is public. Its files, history, issues, PRs, comments, release notes, and Actions logs are readable by anyone. People and automation follow the same rules:

- **Orgs:** examples and reports use `cli-test` or the placeholder slugs (`acme`, `globex`). Never name a customer or any other org. Redact org lists from pasted `syllable status`/`envs` output.
- **Internal details:** no internal ticket IDs or links, internal hostnames, people's emails, or real phone numbers. Fixture IDs live in Actions variables.
- **Platform bugs:** describe them neutrally, as what the API does versus what the spec says, with a repro. Process commentary (ticket states, asks of other teams) belongs in the internal tracker.
- **Security defects** (credential exposure, cross-user data): report them privately as a draft security advisory (`gh api -X POST repos/asksyllable/syllable-cli/security-advisories …`), never as a public issue.
- **Automation:** comment at most once per real state change. Never repeat the same reminder.

## Build and test

```bash
cd scripts/syllable-cli
go build -o syllable .
go test ./...
```

CI ([test.yml](.github/workflows/test.yml)) runs Go vet, race-enabled unit tests, Python spec-drift regressions, and the pinned SDK differential suite on pull requests and pushes to main. The live `integration` package is excluded from this job by its build tag because it requires platform credentials (see below). `main` requires two checks to merge: `test`, and `cask-verify` ([cask-verify.yml](.github/workflows/cask-verify.yml)), which passes when `Casks/` is untouched and otherwise verifies the cask mechanically.

## Test conventions

**Stubbed HTTP for unit tests.** The CI suite never hits a live API. See `setupTestServer` ([cmd/cmd_test.go:20](scripts/syllable-cli/cmd/cmd_test.go#L20)) for the canonical command-test pattern: it wires `apiClient` to an `httptest.Server` so you assert method, path, and body inside the handler. New commands should add a test mirroring `TestOutboundBatchesDelete` / `TestOutboundBatchesResults`.

A few special-case patterns to mirror, not reinvent:

- **Stdin (`--file -`)** — save/restore `os.Stdin` around an `os.Pipe`. See `TestDirectoryUploadStdin`.
- **Endpoint path contracts** — when slash placement matters (the API drops the `Syllable-API-Key` header on a 307 redirect), add an assertion to `internal/spec/spec_test.go`. See `TestBulkOperationPathsMatch`.

For everything else, `--dry-run` prints the request that would be sent without executing it — the safe smoke test when you don't want live calls.

### Live integration tests

`scripts/syllable-cli/integration/` is a black-box suite that builds the CLI binary as a subprocess and exercises it against a live Syllable instance. It is gated behind the `integration` build tag **and** an auth env var, so it never runs from a plain `go test ./...` (including the GoReleaser pre-release hook). It is **opt-in**, run by the developer:

```bash
cd scripts/syllable-cli
SYLLABLE_API_KEY=... go test -tags integration ./integration/...
# or
SYLLABLE_ORG=sandbox go test -tags integration ./integration/...
```

Without `-tags integration` the suite's files are excluded from the build, so `go test ./...` reports no tests for the package and makes no live calls. `SYLLABLE_API_KEY` is read directly by the CLI (no config file needed — this is how CI authenticates); `SYLLABLE_ORG` instead resolves the key from `~/.syllable/config.yaml`. **Do not point integration tests at customer orgs** — use a dedicated throwaway org such as `cli-test`. The org slugs in [AGENTS.md](AGENTS.md) examples (`acme`, `globex`, etc.) are placeholders, not test targets.

## Branch and release workflow

- Feature branches; squash-merge into `main`. Commit titles end with `(#NN)`.
- Semver: `feat:` → minor bump, `fix:` → patch. Majors (`feat!:` or a `BREAKING CHANGE` footer) are always tagged by a human.
- **Releases are automatic.** After every successful **Spec Live Check** on `main` (each push that touches the CLI, plus the daily run), the [Release Train](.github/workflows/release-train.yml) runs [`scripts/ci/release_train.py`](scripts/ci/release_train.py):
  - **Releasable commits:** commits since the last tag with a `feat:`/`fix:` title or `chore: sync CLI to OpenAPI spec` that change shipped code (`scripts/syllable-cli/`, excluding tests). Docs, CI, test, and dependency-only changes ride along with the next real release.
  - **Version:** minor if any releasable commit is a `feat`, otherwise patch.
  - **Release:** the train tags that exact live-checked commit, calls `release.yml`, and writes the release notes from each PR's `## Release notes` section, falling back to its title.

  To preview, run `gh workflow run release-train.yml` (a dry run by default); add `-f dry_run=false` to release now. A hand-pushed `v*` tag still releases through `release.yml`, for majors and emergencies:

```bash
git tag -a vX.Y.Z -m "vX.Y.Z: <short message>"
git push origin vX.Y.Z
```

- [release.yml](.github/workflows/release.yml) (called by the train, or triggered by a pushed `v*` tag) runs GoReleaser, which:
  - Runs `go test ./...` as a pre-release hook.
  - Builds darwin/linux/windows binaries for amd64/arm64 (windows/arm64 excluded).
  - Publishes the GitHub release with tarballs, zip, checksums, and `install.sh`.
  - Opens a PR titled `chore: update Homebrew cask for syllable vX.Y.Z` that updates `Casks/syllable.rb`. The same release run then verifies and merges it ([`scripts/ci/merge_cask_pr.sh`](scripts/ci/merge_cask_pr.sh)). [`verify_cask.py`](scripts/ci/verify_cask.py) checks that the PR changes only the cask, that every url/sha256 pair matches the release's checksums file for all four platforms, and that nothing else in the cask changed (block reordering by a GoReleaser upgrade is tolerated). GitHub runs no workflows on a PR opened with `GITHUB_TOKEN`, so the script records `cask-verify` and `test` as commit statuses before merging. To retry for a tag, run the **Cask Merge** workflow (`gh workflow run cask-merge.yml -f tag=vX.Y.Z`). Nobody approves cask PRs by hand.

## Spec sync

The CLI develops against the embedded OpenAPI spec at `scripts/syllable-cli/internal/spec/openapi.json`, sourced from the `main` branch of [asksyllable/syllable-sdk-typescript](https://github.com/asksyllable/syllable-sdk-typescript). The canonical raw URL:

```
https://raw.githubusercontent.com/asksyllable/syllable-sdk-typescript/main/openapi.json
```

Drift is **detected automatically**, and reconciliation is assisted — but the embedded spec and the code that implements it must always move **together** (never merge a spec-only bump, or `schema get` will advertise endpoints the CLI can't call).

**Detection — [`spec-drift.yml`](.github/workflows/spec-drift.yml).** Runs daily and on demand (`workflow_dispatch`). Fetches the upstream spec, compares it to the embedded copy by `sha256` (`info.version` is an unreliable signal — it rarely bumps when schemas change), and on a real *structural* change files/updates a single rolling **`spec-drift`** issue with the diff, auto-closing it when the spec is back in sync. It is also the routine's **stall watchdog**: if drift sits unreconciled longer than the `SPEC_SYNC_STALL_HOURS` repository variable (default 192 hours, sized for the weekly schedule) with no active (non-draft) reconciliation PR — the usual cause is that the laptop scheduler firing the local routine isn't running — it nags @yorkable on the issue, at most once per window. Keep the variable at the routine's schedule interval plus a day; a shorter window makes every normal wait between fires look like an outage. The watchdog runs in GitHub's cloud, so it keeps working precisely when the laptop doesn't.

**The spec-sync bot — [`spec-sync-bot.yml`](.github/workflows/spec-sync-bot.yml), no AI involved.** Runs daily after drift detection, and on demand. It fetches upstream at a pinned commit and classifies the change with [`scripts/ci/classify_drift.py`](scripts/ci/classify_drift.py), which uses the CLI's own operation map (`syllable __operations`, a hidden command) to tell `--file` pass-through bodies from bodies built out of inline flags.
- **Safe changes** ship by themselves:
  - new optional fields, schemas, enum values, and query parameters;
  - deprecations;
  - widened or loosened rules;
  - response-only changes;
  - server-side tightening of pass-through bodies.

  The bot commits the spec and skill marker to `spec-sync/bot`, runs the full `test` workflow on that exact commit, records `test`/`cask-verify` as commit statuses (bot PRs trigger no workflows), and merges. It then runs the live check on `main` and the release train.
- **Breaking changes** become one plain-language `spec-decision` issue. Adding the `decision:accept` label ships exactly that change; if upstream moves first, the bot replaces the issue.
- **Added or removed operations** need command changes. The bot says so once on the `spec-drift` issue, and the routine below (or a person) reconciles them.

**Reconciliation + release — the [`syllable-sync` skill](.claude/skills/syllable-sync/SKILL.md), driven by one routine.** The skill diffs old vs new, replaces the embedded JSON, updates `cmd/*.go` files and docs, runs tests, and commits in three logical groups (spec / code / docs). Run it by hand, or have a single scheduled **Claude Code routine** carry the whole cycle — detect drift → reconcile → independently verify → merge (the Release Train then releases it) — using the committed prompt at [`routines/full-cycle.md`](.claude/skills/syllable-sync/routines/full-cycle.md) (the canonical source of truth, not a local copy). It is written as an **idempotent state machine**: each run advances only the next un-done step from the live GitHub state, so a re-fire (e.g. after the laptop slept through the schedule) can never re-merge or re-release. It acts automatically **only on purely-additive changes with every gate green**; anything breaking, ambiguous, or not-green it opens as a draft or leaves for a human. A prod *deployment* gap — the spec advertises an endpoint prod doesn't serve yet — is **tracked, never gated**: the command ships spec-true (it starts working when the backend deploys), noted in the release notes and a `prod-drift` issue; holding one endpoint once parked the whole pipeline for weeks (#162) while humans synced by hand. The routine also updates the usage-skill docs (`.claude/skills/syllable-cli/SKILL.md` marker + highlights) as part of each sync PR. The independent-verify step runs as a **fresh subagent** that re-derives the diff from source and reads the actual CI results — so the routine can self-merge without trusting its own reconciliation prose. **Run it locally** with your own git credentials (AI may not run in CI). Schedule it **daily** in the Claude desktop app's Scheduled tasks; since a no-change fire is cheap and new API surface then reaches users within a day (keep `SPEC_SYNC_STALL_HOURS` at the schedule interval plus a day). The scheduled task holds only the short pointer prompt from the top of `full-cycle.md`, so a merged change to the routine takes effect on its next fire with no re-paste.

**What blocks the routine, and what doesn't.** Breaking changes (removed commands, flags, paths, enum values, or response fields; a newly-required field on a body the CLI builds from inline flags) stop for a human. Server-side tightening of a body a command takes only through `--file` (a newly-required field or new constraint) ships automatically with a release-notes line, because the server enforces it whatever CLI version sends the request (#190, #194). Prod deployment gaps ship and are tracked in `prod-drift` issues.

> Earlier this was two routines — a reconciler that opened the PR and a merger that reviewed and released it an hour later. That split was abandoned because two timers fire together when the machine wakes from sleep, reordering the cycle (the merger runs before the PR or its CI exists). One idempotent routine plus a fresh-subagent verifier keeps the independence the split bought without the race. See [`full-cycle.md`](.claude/skills/syllable-sync/routines/full-cycle.md) for the full rationale.

**Cross-repo contract — keeping the docs in sync, safely.** A second routine lives in `asksyllable/ai-specialist` and maintains that repo's `syllable-cli` skill docs. The two are wired as a **straight line, not a loop**: this repo's routine produces **GitHub releases**; the ai-specialist routine consumes them (its cursor is a `Docs synced to CLI vX.Y.Z` marker in its `SKILL.md`, and it processes every release since). The docs routine never changes this repo's code — it only **files issues** here, in the **`prod-drift`** queue, when it live-tests a shipped field on the `cli-test` org and finds prod silently ignores it (e.g. #100). Those issues are owned by a human / the backend, are deduped by command + field so the same drift isn't re-filed daily, and the docs routine drops its own caveat once a re-test passes. The system converges because **this repo's routine only ever watches the upstream SDK spec** — an ai-specialist issue is invisible to it, so the only path from an issue back to a CLI change runs through a human. No autonomous cycle exists.

**Live validation — [`spec-live-check.yml`](.github/workflows/spec-live-check.yml).** Catches spec-vs-reality drift by building the CLI and running the integration suite against a **dedicated, non-customer CI org**, authenticating with the `SYLLABLE_CI_API_KEY` repo secret. Runs daily, on demand, and on every push to `main` that touches `scripts/syllable-cli/**`, never on PR branches: the job holds the API key while it runs the code it checks out, so it only runs trusted code. Reconciliation PRs carry a local `cli-test` live-suite summary instead, and the routine won't tag a release until the live check passed for that `main` commit. The run uses no overlapping concurrency, and enables the `cli-test` fixtures (repo variables) only after confirming the key belongs to that org (`SYLLABLE_TEST_ORG_SLUG`). **The secret must be a key for that CI org, never a customer key** — the key itself is the org boundary (`SYLLABLE_ORG` is left unset; CI has no `~/.syllable/config.yaml`). If the secret is missing the run fails rather than passing silently.

**The diff script — [`diff_specs.py`](.claude/skills/syllable-sync/scripts/diff_specs.py)** (committed in the repo, so CI and the skill share one copy). Reports new/removed paths and methods, deep operation/schema contract changes, and enum members (a removed enum value is flagged as breaking). Deep comparison includes query/path parameters, request/response schemas, defaults, required fields, nullable types, validation constraints, servers, security schemes, and shared components; prose and irrelevant ordering are ignored. The earlier shallow field-type comparison could miss changes inside unions and parameters on existing operations. Regression tests run in CI via `python3 -m unittest discover -s .claude/skills/syllable-sync/scripts -p 'test_*.py'`. For CI/scripting it takes `--exit-code` (1 = structural differences, 0 = equivalent, 2 = usage error) and `--format json`:

```bash
python3 .claude/skills/syllable-sync/scripts/diff_specs.py --exit-code \
  scripts/syllable-cli/internal/spec/openapi.json /tmp/upstream.json
```

### Activating this automation

The workflows ship in the repo, but a few one-time setup steps are required (until then `spec-drift.yml` works, but the live check and the routine's labeling don't):

1. **Add the CI-org secret.** Create repository secret `SYLLABLE_CI_API_KEY` (Settings → Secrets and variables → Actions) holding the API key for a **dedicated, non-customer CI org** — never a customer key. Until it exists, `spec-live-check.yml` skips with a warning rather than failing.
2. **Create the labels.** Trigger `spec-drift.yml` once via **workflow_dispatch** — it creates both `spec-drift` and `spec-sync`. Or by hand: `gh label create spec-sync -c 0E8A16 -d "Reconciliation PR"`. The `spec-sync` label marks reconciliation PRs and must exist before the routine can apply it.
3. **Set up the spec-sync routine** (recommended) — see *Reconciliation + release* above. Paste the pointer prompt from the top of [`full-cycle.md`](.claude/skills/syllable-sync/routines/full-cycle.md), not the whole file.
4. **Allow the routine's commands on its machine.** Unattended, Claude Code's auto-mode permission check decides every command no allow rule covers, and it has denied this routine's merges, tag pushes, and live test calls. Add these to `permissions.allow` in this repo's `.claude/settings.local.json` (local only, never committed):

   ```json
   "Bash(git fetch *)", "Bash(git switch *)", "Bash(git pull *)", "Bash(git add *)",
   "Bash(git commit *)", "Bash(git tag *)", "Bash(git push *)", "Bash(git ls-remote *)",
   "Bash(gh pr *)", "Bash(gh issue *)", "Bash(gh release *)", "Bash(gh run *)", "Bash(gh workflow run *)",
   "Bash(go test *)", "Bash(go build *)", "Bash(go vet *)",
   "Bash(npm ci --prefix tests/sdk-parity *)", "Bash(npm test --prefix tests/sdk-parity)",
   "Bash(python3 .claude/skills/syllable-sync/scripts/diff_specs.py *)",
   "Bash(curl -fsSL https://raw.githubusercontent.com/asksyllable/syllable-sdk-typescript/*)",
   "Bash(syllable --org cli-test *)"
   ```

   The routine runs each of these as a standalone command; chained irreversible commands still go to the permission check. If a run reports a denied command, add a rule for it rather than running the step by hand.

`spec-drift.yml` itself needs no setup; it runs on the default `GITHUB_TOKEN`.

## Convention notes

- All `--file` flags accept `-` to read from stdin. Multipart upload commands gained stdin support in v1.4.0; before that, `--file -` would silently fail by trying to open a literal file named `-`.
