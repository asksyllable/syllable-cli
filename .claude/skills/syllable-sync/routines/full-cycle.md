# Routine: spec-sync full cycle (detect → reconcile → verify → merge → release → Homebrew)

**Canonical prompt for the spec-sync routine.** The scheduled task does not carry a copy of this prompt. It carries the short pointer below, which pulls `main` and follows this file, so a merged change here takes effect on the next fire. Hand-pasted copies lagged this file twice (the v1.7.2 stall, and #189's cask fix still missing locally a day after it merged). Because the routine executes whatever this file says on `main` with release rights, `.claude/skills/syllable-sync/` is CODEOWNERS-gated.

> **Scheduled-task prompt (paste once into the routine; never needs re-pasting):**
> You are the spec-sync routine for `asksyllable/syllable-cli`. Work in `~/Documents/Claude/syllable-cli`. First get onto a clean, current `main` with three separate commands: `git fetch origin`, then `git switch main`, then `git pull --ff-only`. Then read `.claude/skills/syllable-sync/routines/full-cycle.md` and follow everything after its first `---` line as your instructions for this run. If the pull fails or the file is missing, stop and say so; never fall back to a remembered or older copy of the instructions.

> **Why one routine, and why a state machine.** The earlier design split this across two timed routines (reconciler, then merger an hour later) so an *independent* session would re-derive the truth from source rather than trust the first session's review prose. That independence is real and worth keeping — the hard-won lesson is that a self-review and a second-model review can share the same blind spot, and what actually decides correctness is re-running the diff on the right baseline and reading the actual test JSON. But two timers have a failure mode: if the machine is asleep at both scheduled times, macOS fires **both at once** on wake, and the merger runs before the reconciler's PR (or its CI) even exists. Collapsing to one routine fixes that cross-timer race; running the verify step as a **fresh subagent** preserves the independence (it re-derives from the specs and reads the actual CI results with no view of this session's reasoning). The remaining risk is that one long cycle can itself be interrupted mid-way by sleep — so the routine is written as an **idempotent state machine**: each run observes the live GitHub state and does only the next un-done step. A re-fire can never re-merge, re-tag, or re-release, and the easy-to-lose final step — merging the Homebrew cask — becomes un-droppable.

**Four operating requirements:**

1. **Releasing no longer depends on this routine.** The `release-train.yml` workflow tags, builds, publishes, merges the Homebrew cask, and writes notes in GitHub after each green live check on `main`. This routine reconciles the spec and opens PRs; it runs locally with your git credentials.
2. **One fire finishes the job; firing often is still better.** A single run waits for CI and the release build and carries the whole cycle through (open PR → verify → merge → tag → release → cask), so even a weekly schedule ships a full release per run. A no-change fire costs one short session, so **daily** is the better schedule: new API surface reaches users within a day instead of up to a week, and a sleep-interrupted run heals the next morning. Every irreversible action is guarded against live state, so a re-fire is always safe; just don't run two overlapping copies on the same schedule.
3. **A cloud watchdog backstops a dead scheduler.** This routine fires only while its host scheduler is alive (for a desktop-app routine: the app must be running on that machine). If it goes quiet, the stall watchdog in `spec-drift.yml` nags @yorkable on the drift issue once drift has sat unreconciled, with no active reconciliation PR, for longer than the `SPEC_SYNC_STALL_HOURS` repository variable (default 192 hours, sized for a weekly schedule; set it to about 48 for a daily one). Keep it at the schedule's interval plus a day, or every normal wait between fires looks like an outage. The durable fix for a real alarm is to get the scheduler firing again (reopen the app, check the routine's last-run time), not to hand-run the cycle; hand-runs hide the outage and it recurs.
4. **Unattended runs need explicit permission rules.** With nobody watching, Claude Code's auto-mode permission check decides every command that no allow rule covers, and it has denied this routine's merges, tag pushes, and live test calls. On the routine's machine, `.claude/settings.local.json` must allow the commands listed under *Activating this automation* in `CONTRIBUTING.md`. A permission denial is a configuration gap: the prompt below tells the routine to report it instead of working around it.

---

You are the spec-sync routine for `asksyllable/syllable-cli`: a single session that carries an upstream OpenAPI spec change all the way to a published release and a merged Homebrew cask — **but only when the change is purely additive and every gate is green**. Anything breaking, ambiguous, or not-green you route to a human. You are the last gate before users; when in doubt, do not merge or publish.

This routine runs **locally** from `~/Documents/Claude/syllable-cli` with the user's own git credentials. Releases are made by the `release-train.yml` workflow in GitHub, not by you.

**Work as a state machine, not a script.** Each run: get onto a clean `main` (`git fetch origin`, `git switch main`, `git pull --ff-only`, as separate commands), then work out where the cycle already is from the live GitHub state, start at the **first un-done step**, and **carry the cycle as far forward as it will go in this single run** — do not park after opening the PR. When a step kicks off CI or a release build (opening the PR in B, pushing the tag in F), **wait for it to finish** — poll `gh pr checks <n>` / `gh run list --workflow=release.yml` for up to ~15 minutes — then continue straight to the next applicable step in the same run. Stop and let a later fire resume only if it is still not done after that wait, or you are interrupted. Because every step first re-observes the live GitHub state, never assume a step "must" have run (check), and stopping or re-firing at any point is always safe. Always end by stating which state you found and what you did, so the run is auditable.

**When you stop and leave something for a human** — a breaking/ambiguous change, a failed check, or a failed release build — don't rely on anyone noticing. Comment with the specifics **and a recommended action**, then assign the PR (or the `spec-drift` issue) to **@yorkable** and @-mention him so GitHub emails him. This routine should reach out **only** when it is genuinely blocked; the additive happy path runs start-to-finish in silence.

**Public repo hygiene.** This repository is public, so every PR, issue, comment, commit message, and release note you write is readable by anyone. Follow the *Public repo hygiene* rules in `CONTRIBUTING.md`:
- name only `cli-test` (never a customer or other org);
- no internal ticket IDs, internal hostnames, emails, or phone numbers;
- describe platform bugs neutrally with a repro, and put no process commentary about other teams in public;
- send security defects to a draft security advisory, not an issue;
- comment once per real state change, never a repeated reminder.

**Command hygiene (you run unattended).** Run each irreversible command (`gh pr merge`, `gh pr review --approve`, `git tag`, `git push`) as its own standalone command: target the repo with `--repo asksyllable/syllable-cli` or `git -C <path>`, and never chain it after `cd`, `&&`, or `;`. Unattended permission checks evaluate chained irreversible commands far more strictly and have blocked them. Run live CLI probes the same way, one `syllable --org cli-test --env prod …` command per call, never against another org. If a permission check denies a command, don't retry it or look for another route to the same effect: comment on the PR (or the `spec-drift` issue) with the exact denied command, @-mention @yorkable so the permission rule can be added, and stop.

**Gather the state first**, then match the first applicable case A–I below:
- Open `spec-sync` PRs: `gh pr list --label spec-sync --state open --json number,isDraft,title` (if several non-draft, take the oldest).
- Drift: download `https://raw.githubusercontent.com/asksyllable/syllable-sdk-typescript/main/openapi.json` and run `python3 .claude/skills/syllable-sync/scripts/diff_specs.py --exit-code scripts/syllable-cli/internal/spec/openapi.json <downloaded.json>` (exit 1 = real structural drift).
- The post-merge tail: latest release (`gh release view --json tagName,createdAt,body`), most recent merged spec-sync PR (`gh pr list --label spec-sync --state merged --limit 1 --json number,mergedAt,title`), open Homebrew cask PR (`gh pr list --search "update Homebrew cask in:title" --state open`), open `spec-drift` issue (`gh issue list --label spec-drift --state open`).

**If more than one case applies, finish an in-flight release first** — work the tail (F → G → H → I) before starting a new reconcile (B), so a published release is never left without its Homebrew cask.

**A. No open spec-sync PR, no drift, and the tail (F–I) is clean** → nothing to do. Stop.

**B. Drift, and no open spec-sync PR** → reconcile. Run the **`syllable-sync`** skill end to end on a new branch: diff → replace the embedded spec → update `cmd/*.go` + `cmd/root.go` + `README.md`/`AGENTS.md` → `cd scripts/syllable-cli && go test ./...`, plus integration tests for any new commands, plus the SDK differential suite (`npm ci --prefix tests/sdk-parity --ignore-scripts --no-audit --no-fund && npm test --prefix tests/sdk-parity`). Commands newer than the pinned SDK are logged there as "parity pending", not failures; bump the SDK pin only per the skill's checklist, and never hold a sync for an SDK release. Also update the **usage skill** (`.claude/skills/syllable-cli/SKILL.md`): document the new surface in the relevant sections, bump the `Docs synced to CLI vX.Y.Z` marker, and add a highlights entry — compute `vX.Y.Z` the same way step F does. Commit spec + code + docs **together** (the spec must never land ahead of the code).

**Prod deployment is tracked, never gated.** Live-probe each NEW endpoint against the `cli-test` org on prod (e.g. request a nonexistent id): a deployed route answers with a structured, parameter-aware error such as `"Session not found: <id>"`, while an undeployed one returns the router's bare `404 {"detail":"Not Found"}`. An undeployed endpoint **still ships** — the command is spec-true and starts working the moment the backend deploys — but add a "not yet deployed on prod" line to the PR body and the Release notes, and file/update a **`prod-drift`** issue for it (content-deduped: search open `prod-drift` issues for that path first). Never draft or hold a PR over a deployment gap: holding one endpoint once parked the whole pipeline for weeks (#162) while other drift accumulated and humans had to sync by hand.

Open a PR — title **`feat: sync CLI to OpenAPI spec`** if it adds commands/flags (bumps the minor version and shows in the changelog), else **`chore: sync CLI to OpenAPI spec`** for field-only syncs. Body must include: the `diff_specs.py` report; a **Breaking changes** section; a **Release notes** section (short, human-readable, written for end users — the release step uses it verbatim); and `Closes #<the spec-drift issue number>`. Apply the **`spec-sync`** label (it marks reconciliation PRs; the live check no longer runs on PRs, see F). Before opening the PR, run the live integration suite locally against `cli-test` with the branch build (the fixture command in CONTRIBUTING's *`cli-test` fixtures* section) and put the pass/skip summary in the PR body.

**What counts as breaking** is anything that makes a working CLI invocation or script stop working: removed commands, flags, or paths; **removed enum values**; removed or renamed response fields; and a newly-required field or narrowed type on a request body the CLI builds from inline flags. **Server-side tightening of a pass-through body is not breaking.** When a newly-required field, a narrowed type, or a new constraint (`minItems`, `minimum`, `pattern`, non-blank, …) lands on a request body that the affected command accepts only through `--file`/stdin, no CLI change can help: the server enforces the rule whatever CLI version sends the request, so holding the release protects nobody. List the new requirement in **Release notes** and ship it (precedents: #190, #194). To confirm a body is pass-through, run the command's `--help` on the PR build: if any flag other than `--file` sets that body's fields, it is CLI-built and the change is breaking.

If the change is breaking, ambiguous, or a review surfaces something you can't safely fix → open the PR as a **draft** and summarize the decision needed. Otherwise **wait for CI to finish** (poll up to ~15 min) and continue to the verify/merge step (E) in the same run; defer to a later fire only if CI is still pending after that wait.

**C. A *draft* spec-sync PR is open** → a draft is never yours to merge, no matter what. What you do next depends on *why* it is a draft (read its body and comments):
- **Drafted for a breaking or ambiguous change** → stop, exactly as before: the decision belongs to a human. One addition so it can't rot silently: if the newest @yorkable ping on the PR is older than 72 hours **and** something material changed since it (a new breaking change or a new decision behind the draft, not just more additive drift), post one reminder comment noting its age and what changed, then stop. Seventy-two hours is a ceiling on reminders, not a metronome: repeating the same ask trains people to ignore the routine. (Don't open a second spec-sync PR alongside a breaking draft — both replace the same embedded spec and would conflict; the human must decide the draft first.)
- **Drafted only over a prod deployment gap** (the spec advertises an endpoint prod didn't serve yet, nothing breaking in the diff) → per the policy in B, deployment gaps are tracked in a `prod-drift` issue, not held. Close the draft with a comment that a fresh sync supersedes it, then go to **B** and reconcile from current upstream; the normal B–E gates (purely additive + every check green + independent verify) still apply in full to the new PR.

**D. A non-draft spec-sync PR is open, but its checks are not all green** → do not merge. Read `gh pr checks <n> --json name,state,bucket`. The required checks are `test` and `cask-verify`. If anything is pending/queued/in-progress, **wait** (poll up to ~15 min); once everything is green, proceed to E in the same run. Defer to a later fire only if checks are still running after that wait. If a required check FAILED, comment with the specific failure and leave it for a human.

**E. A non-draft spec-sync PR is open and every check is green but it's unmerged** → verify independently, then merge. **Spawn a fresh subagent** (Task tool) and give it ONLY the PR number and the job below — do not pass it your own conclusions, and tell it explicitly not to read the PR's review comments first:

> Re-derive the diff yourself. `gh pr checkout <n>`, then diff the PR's `scripts/syllable-cli/internal/spec/openapi.json` against `git show origin/main:scripts/syllable-cli/internal/spec/openapi.json` using `python3 .claude/skills/syllable-sync/scripts/diff_specs.py --format json <base> <pr>`. Return **three booleans with evidence**: (1) `additive` — the diff shows only new paths/commands, new *optional* fields, new enum values, and server-side tightening of **pass-through** request bodies (a newly-required field, narrowed type, or new constraint on a body that its command accepts only via `--file`; prove it by building the PR (`cd scripts/syllable-cli && go build -o /tmp/syllable-pr .`) and showing that the command's `--help` has no other flag setting that body's fields); nothing removed, nothing tightened on a CLI-built body, nothing semantically changed (a removed enum value is breaking); (2) `gates_green` — from `gh pr checks <n> --json name,state,bucket`: `test` = SUCCESS and `cask-verify` = SUCCESS, every other check SUCCESS or SKIPPED, and the PR body carries a local live-suite summary against `cli-test` with no failures (the CI live check runs on `main` after merge, never on PR code); (3) `tests_present` — each new command path has an integration test. Also spot-check trailing slashes (a collection path ends in `/`, an item path does not — a mismatch drops the `Syllable-API-Key` header on a 307) and int-vs-string IDs.

Merge **only if the subagent returns `additive && gates_green && tests_present` all true**. The decision is those three booleans against the tool output — **not** anyone's prose, including the subagent's narrative, the PR's own review comments, or your first impression. If any is false or uncertain → comment with specifics and leave it for a human. If all true: `gh pr merge <n> --squash --delete-branch`, confirm the linked `spec-drift` issue closed (close it if not), then continue **in the same run** to step F.

**F. There are merged spec-sync changes that aren't released yet** (the most recent merged spec-sync PR is newer than the latest published release) → **don't tag; the Release Train does.** After every successful `Spec Live Check` on `main`, the `release-train.yml` workflow decides whether there is a releasable change, computes the version (`feat:` → minor, otherwise patch), tags that exact live-checked commit, builds and publishes the release, merges the Homebrew cask, and writes the release notes from the PRs' **Release notes** sections. Your job here is only to confirm it happened:
- **A release run is in progress** (`gh run list --workflow=release-train.yml --limit 3`) → wait for it (poll up to ~15 min), then continue to H.
- **The live check for the merged commit failed** (`gh run list --workflow=spec-live-check.yml --branch main --limit 5 --json headSha,conclusion`) → the train correctly did not release. Comment on the merged PR with the failing run, @-mention @yorkable, and stop.
- **The live check passed more than 30 minutes ago and there is still no release** → start the train by hand: `gh workflow run release-train.yml --repo asksyllable/syllable-cli -f dry_run=false`, wait for it, and continue. If it fails, comment with the failing run, @-mention @yorkable, and stop.
- **The train opened a "Release train held: breaking change" issue** → a major version is a human decision. Leave it.

Never push a tag yourself while the train is enabled; a hand-pushed tag still releases (`release.yml` runs on any `v*` tag push), but it races the train.

**G. The latest release is published but its notes are still empty or a bare `## Changelog`** (the train normally writes them; this is the fallback) → set them from the merged PR's **Release notes** section (GoReleaser's commit changelog omits `chore:`/field-only changes, so never ship empty notes). Continue to H.

**H. The `chore: update Homebrew cask …` PR is still open** → the release workflow normally verifies and merges it by itself, right after GoReleaser (`scripts/ci/merge_cask_pr.sh`, which runs `scripts/ci/verify_cask.py --cask-only`: every url/sha256 pair must match the release checksums, all four platforms present, no structural change). If the release run finished more than 10 minutes ago and the PR is still open, re-run that step with `gh workflow run cask-merge.yml --repo asksyllable/syllable-cli -f tag=vX.Y.Z` and wait for it (poll `gh run list --workflow=cask-merge.yml`). If it fails, the verifier's output says why: comment with it, @-mention @yorkable, and stop. Never approve or merge a cask PR by hand. Continue to I.

**I. Everything above is done but the `spec-drift` issue is still open** (and there's no remaining drift) → close it.

**If anything is off at any step** — a breaking or ambiguous change, your re-derived diff disagrees with the PR, a red or missing gate, a new command without a test — **comment with specifics and leave it for a human. Never merge, tag, or publish on doubt.**
