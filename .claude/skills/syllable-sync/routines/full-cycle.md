# Routine: spec-sync full cycle (detect → reconcile → verify → merge → release → Homebrew)

**Canonical prompt for the spec-sync routine.** Paste the prompt below into a *single* scheduled Claude Code routine (`/schedule`, the desktop app, or [claude.ai/code/routines](https://claude.ai/code/routines)) with the `asksyllable/syllable-cli` repo selected. This one routine replaces the former reconciler + merger split. This file is the source of truth — change it here and re-paste.

> **Why one routine, and why a state machine.** The earlier design split this across two timed routines (reconciler, then merger an hour later) so an *independent* session would re-derive the truth from source rather than trust the first session's review prose. That independence is real and worth keeping — the hard-won lesson is that a self-review and a second-model review can share the same blind spot, and what actually decides correctness is re-running the diff on the right baseline and reading the actual test JSON. But two timers have a failure mode: if the machine is asleep at both scheduled times, macOS fires **both at once** on wake, and the merger runs before the reconciler's PR (or its CI) even exists. Collapsing to one routine fixes that cross-timer race; running the verify step as a **fresh subagent** preserves the independence (it re-derives from the specs and reads the actual CI results with no view of this session's reasoning). The remaining risk is that one long cycle can itself be interrupted mid-way by sleep — so the routine is written as an **idempotent state machine**: each run observes the live GitHub state and does only the next un-done step. A re-fire can never re-merge, re-tag, or re-release, and the easy-to-lose final step — merging the Homebrew cask — becomes un-droppable.

**Two operating requirements:**

1. **Run it where its tag-push triggers the release.** The release only fires if the `vX.Y.Z` tag is pushed with credentials GitHub lets trigger workflows. A tag pushed by the default GitHub Actions token is deliberately suppressed (loop-prevention), so the build and Homebrew update would **silently never happen**. Run this routine locally with your own git credentials (or give it a PAT).
2. **It's safe — and good — to fire often.** Because each run only advances the next un-done step and guards every irreversible action against the live state, schedule it **hourly** (not once a day) so a cycle interrupted by sleep heals within the hour. A typical additive change takes ~3 fires (open PR → wait CI; merge + tag → wait build; set notes + merge cask + close issue), so daily firing would stretch one release across days. Just don't run two overlapping copies on the same schedule — one is enough.

You are the spec-sync routine for `asksyllable/syllable-cli`: a single session that carries an upstream OpenAPI spec change all the way to a published release and a merged Homebrew cask — **but only when the change is purely additive and every gate is green**. Anything breaking, ambiguous, or not-green you route to a human. You are the last gate before users; when in doubt, do not merge or publish.

**Work as a state machine, not a script.** Each run: get onto a clean `main` (`git fetch origin && git switch main && git pull --ff-only`), then work out where the cycle already is from the live GitHub state and do **only the first un-done step**, then stop. This is what makes it safe to re-run after an interruption — never assume a step "must" have run; check. You may poll briefly (a few minutes) for CI or the release build to finish within a run; if it's taking long, just stop and let the next fire resume. Always end by stating which state you found and what you did, so the run is auditable.

**When you stop and leave something for a human** — a breaking/ambiguous change, a failed check, or a failed release build — don't rely on anyone noticing. Comment with the specifics **and a recommended action**, then assign the PR (or the `spec-drift` issue) to **@yorkable** and @-mention him so GitHub emails him. This routine should reach out **only** when it is genuinely blocked; the additive happy path runs start-to-finish in silence.

**Gather the state first**, then match the first applicable case A–I below:
- Open `spec-sync` PRs: `gh pr list --label spec-sync --state open --json number,isDraft,title` (if several non-draft, take the oldest).
- Drift: download `https://raw.githubusercontent.com/asksyllable/syllable-sdk-typescript/main/openapi.json` and run `python3 .claude/skills/syllable-sync/scripts/diff_specs.py --exit-code scripts/syllable-cli/internal/spec/openapi.json <downloaded.json>` (exit 1 = real structural drift).
- The post-merge tail: latest release (`gh release view --json tagName,createdAt,body`), most recent merged spec-sync PR (`gh pr list --label spec-sync --state merged --limit 1 --json number,mergedAt,title`), open Homebrew cask PR (`gh pr list --search "update Homebrew cask in:title" --state open`), open `spec-drift` issue (`gh issue list --label spec-drift --state open`).

**If more than one case applies, finish an in-flight release first** — work the tail (F → G → H → I) before starting a new reconcile (B), so a published release is never left without its Homebrew cask.

**A. No open spec-sync PR, no drift, and the tail (F–I) is clean** → nothing to do. Stop.

**B. Drift, and no open spec-sync PR** → reconcile. Run the **`syllable-sync`** skill end to end on a new branch: diff → replace the embedded spec → update `cmd/*.go` + `cmd/root.go` + `README.md`/`AGENTS.md` → `cd scripts/syllable-cli && go test ./...`, plus integration tests for any new commands. Commit spec + code + docs **together** (the spec must never land ahead of the code). Open a PR — title **`feat: sync CLI to OpenAPI spec`** if it adds commands/flags (bumps the minor version and shows in the changelog), else **`chore: sync CLI to OpenAPI spec`** for field-only syncs. Body must include: the `diff_specs.py` report; a **Breaking changes** section (removed commands/flags, **removed enum values**, newly-required fields, narrowed types); a **Release notes** section (short, human-readable, written for end users — the release step uses it verbatim); and `Closes #<the spec-drift issue number>`. Apply the **`spec-sync`** label so the live check runs. If the change is breaking, ambiguous, or a review surfaces something you can't safely fix → open the PR as a **draft** and summarize the decision needed. Then **stop** — let CI run; a later fire continues.

**C. A *draft* spec-sync PR is open** → it's flagged for a human. Stop; it is never yours to merge.

**D. A non-draft spec-sync PR is open, but its checks are not all green** → do not merge. Read `gh pr checks <n> --json name,state,bucket`. If `live-check` is **SKIPPED**, the `spec-sync` label is missing so the live QA never ran — apply it (`gh pr edit <n> --add-label spec-sync`), then stop and let the next fire re-check once it runs. If anything is pending/queued/in-progress, stop and let the next fire re-check. If a required check FAILED, comment with the specific failure and leave it for a human.

**E. A non-draft spec-sync PR is open and every check is green but it's unmerged** → verify independently, then merge. **Spawn a fresh subagent** (Task tool) and give it ONLY the PR number and the job below — do not pass it your own conclusions, and tell it explicitly not to read the PR's review comments first:

> Re-derive the diff yourself. `gh pr checkout <n>`, then diff the PR's `scripts/syllable-cli/internal/spec/openapi.json` against `git show origin/main:scripts/syllable-cli/internal/spec/openapi.json` using `python3 .claude/skills/syllable-sync/scripts/diff_specs.py --format json <base> <pr>`. Return **three booleans with evidence**: (1) `additive` — the diff shows only new paths/commands, new *optional* fields, and new enum values; nothing removed, narrowed, newly-required, or semantically changed (a removed enum value is breaking); (2) `gates_green` — from `gh pr checks <n> --json name,state,bucket`: `test` = SUCCESS, `live-check` = SUCCESS (it actually **ran**, not SKIPPED — a SKIPPED live-check means the `spec-sync` label was missing, so the live QA never happened), every other check SUCCESS or SKIPPED; (3) `tests_present` — each new command path has an integration test. Also spot-check trailing slashes (a collection path ends in `/`, an item path does not — a mismatch drops the `Syllable-API-Key` header on a 307) and int-vs-string IDs.

Merge **only if the subagent returns `additive && gates_green && tests_present` all true**. The decision is those three booleans against the tool output — **not** anyone's prose, including the subagent's narrative, the PR's own review comments, or your first impression. If any is false or uncertain → comment with specifics and leave it for a human. If all true: `gh pr merge <n> --squash --delete-branch`, confirm the linked `spec-drift` issue closed (close it if not), then continue **in the same run** to step F.

**F. There are merged spec-sync changes that aren't released yet** (the most recent merged spec-sync PR is newer than the latest published release) → release. Compute the bump from **everything unreleased**, not just the last merge: diff the latest release's spec (`git show <latest-tag>:scripts/syllable-cli/internal/spec/openapi.json`) against current `main` — any new path/command in that range → **minor**; only new fields / enum values → **patch**. That gives `vX.Y.Z`.

Then **guard the irreversible action on the *tag*, not the release** — the tag is created first; the GitHub release only appears after GoReleaser finishes, so a guard that checks the release would re-tag during the build window. Check `git ls-remote --tags origin refs/tags/vX.Y.Z`:
- **Tag absent** → `git tag vX.Y.Z` and push it **with your local credentials** (a tag pushed by the default GitHub Actions token will NOT trigger `release.yml`). Then **stop** — let GoReleaser build; a later fire continues.
- **Tag exists and the release is published** → tagging is done; go to G.
- **Tag exists but no release yet** → do **not** re-tag. Check the build: `gh run list --workflow=release.yml --limit 3`. Still in progress → stop and let it finish. **Failed** → comment on the PR (or the `spec-drift` issue) with the failing run and leave it for a human — a failed build means the tag exists but users will never get the release, which needs a person. Never delete or move a tag automatically.

**G. The latest release is published but its notes are empty or a bare `## Changelog`** → set them from the merged PR's **Release notes** section (GoReleaser's commit changelog omits `chore:`/field-only changes, so never ship empty notes). Continue to H.

**H. The `chore: update Homebrew cask …` PR is open** → **merge it** (`gh pr merge <n> --squash`). This is the final, easy-to-forget step that actually puts the release in front of `brew` users — never skip it. Continue to I.

**I. Everything above is done but the `spec-drift` issue is still open** (and there's no remaining drift) → close it.

**If anything is off at any step** — a breaking or ambiguous change, your re-derived diff disagrees with the PR, a red or missing gate, a new command without a test — **comment with specifics and leave it for a human. Never merge, tag, or publish on doubt.**
